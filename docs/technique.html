RENDRAX · DOCUMENTATION TECHNIQUE

Comment fonctionne le moteur de rendu

Cette page décrit le comportement constaté dans le code du dépôt. Les performances dépendent du contenu HTML, des ressources distantes et de la charge du runner ; aucun temps de rendu fixe n’est garanti.

1. Profils d’animation reconnus

Le moteur examine le HTML et cherche des signatures précises. Un profil reconnu peut être piloté image par image : le moteur fixe le temps de l’animation, capture chaque image et synchronise les pistes audio prises en charge.

ProfilÉléments caractéristiques détectésTraitement
KIDASStructure React attendue, scène .stage, audio intégré en data URI et durée déclarée.Contrôle manuel du temps, capture image par image et extraction des pistes prévues par le profil.
EditProFonction render(t), boucle d’animation attendue, canvas IM et voix encodée en base64.La boucle temps réel est neutralisée ; la voix intégrée est extraite et la scène est rendue à des instants déterminés.
MusicProCanvas et render(t), décodage VOICE, fonctions audio music/go, boucle lp et variables de durée/voix/musique attendues.Le moteur pilote le rendu image par image et récupère les pistes voix/musique décodées par le navigateur.
Vidéo ReactAPI window.__video avec seek(), audio intégré et durée DUR.La boucle pilotée par l’audio est neutralisée ; l’API de la page sert au positionnement temporel.
Vidéo GSAPAudio intégré, déclaration de durée ou tableau de temps, sous-titres SUB, timeline GSAP en pause et appel à tl.time(..., false).La timeline est pilotée directement image par image pour préserver la synchronisation prévue par ce profil.

Les tests de détection reposent sur des signatures de code, pas uniquement sur le nom d’une bibliothèque. Une page qui ressemble visuellement à un exemple mais dont le code diffère peut ne pas être reconnue.

Mode universel : toute page HTML exploitable qui ne correspond pas à l’un des cinq profils est traitée en mode générique. Chromium est capturé en temps réel. La synchronisation audio/vidéo n’est alors pas garantie et certaines animations peuvent perdre en fluidité si les captures prennent trop de temps.

2. Bibliothèques JavaScript externes

RENDRAX ne maintient pas de liste blanche garantissant la compatibilité de toutes les bibliothèques JavaScript. Le principe est de charger la page dans Chromium : une bibliothèque peut fonctionner si son script est accessible, si ses API sont compatibles avec Chromium et si elle ne dépend pas d’une interaction ou d’un service indisponible pendant le rendu.

  • GSAP : des animations GSAP peuvent être rendues en mode synchronisé lorsque leur structure correspond exactement au profil GSAP détecté. Les autres intégrations GSAP passent en mode générique.
  • React : certaines structures React spécifiques sont reconnues par les profils KIDAS ou Vidéo React. Cela ne constitue pas une garantie pour toute application React.
  • Canvas et Web Audio : pris en charge par certains profils identifiés ; les autres implémentations sont traitées selon les possibilités du mode générique.
  • Autres bibliothèques : elles ne sont pas certifiées individuellement. Leur comportement dépend de Chromium, de leur initialisation, de leurs dépendances réseau et de leur mode d’animation.

Les scripts, polices, images et sons hébergés sur un CDN ou un autre domaine doivent rester accessibles depuis le runner. Les erreurs CORS, les restrictions du serveur distant, les changements d’URL ou une connexion indisponible peuvent empêcher leur chargement. Pour fiabiliser un projet, place les ressources essentielles dans l’archive ZIP lorsque c’est possible.

3. Chaîne Chromium et FFmpeg

Chromium

  1. Le runner prépare un répertoire temporaire et sert le projet par un petit serveur HTTP local lié à 127.0.0.1.
  2. Chromium démarre en mode headless avec un profil temporaire et des extensions désactivées.
  3. Le moteur communique avec Chromium au moyen du protocole Chrome DevTools (CDP) pour charger la page, régler la fenêtre, piloter le temps des profils compatibles et capturer des images JPEG.
  4. Pour les profils synchronisés, le moteur demande chaque image à un instant calculé. En mode générique, il capture la page pendant la durée réelle, puis remet les images à cadence constante.

FFmpeg

Les images capturées sont assemblées en MP4. Le chemin d’encodage principal utilise H.264 (libx264) ; si cet encodeur n’est pas disponible, le moteur utilise MPEG-4. La vidéo est produite en pixels yuv420p. Quand une piste audio est disponible, elle est encodée en AAC stéréo à 48 kHz, avec un débit cible de 192 kbit/s. Le conteneur est optimisé pour le démarrage rapide de la lecture (faststart).

QualitéRéglages vidéoUsage
RapideCRF 24, preset ultrafast, capture JPEG qualité 80Aperçu, test ou échelle réduite lorsque la qualité est automatique.
StandardCRF 18, preset veryfast, capture JPEG qualité 90Réglage automatique habituel pour un rendu complet.
ÉlevéeCRF 15, preset slow, capture JPEG qualité 95Option disponible dans le moteur CLI ; le workflow web utilise le choix automatique.

Lorsque l’audio est présent, le moteur vérifie les durées des pistes avec ffprobe et signale les écarts. Pour les profils synchronisés, un écart trop important peut invalider le MP4.

4. GitHub Actions et cycle d’un rendu

  1. L’application envoie le HTML ou le ZIP dans le stockage privé Backblaze B2 avec une URL signée temporaire. La taille du fichier source est limitée à 50 Mo.
  2. Une exécution GitHub Actions est déclenchée manuellement par l’API avec les paramètres du rendu. Le workflow s’exécute sur ubuntu-24.04, installe Python 3.12, FFmpeg/ffprobe et les dépendances Python nécessaires.
  3. Le runner récupère le fichier temporaire au moyen d’un jeton GitHub OIDC vérifié par l’API. Pour un ZIP, il extrait le projet après validation de l’archive.
  4. Le script Python lance Chromium, effectue les captures, puis FFmpeg encode le MP4.
  5. Le workflow crée une miniature, contrôle les métadonnées, envoie le MP4 et la miniature dans B2, puis publie les métadonnées de la vidéo.
  6. Les journaux et la progression sont relayés à l’interface lorsque l’identifiant de tâche est valide. Le workflow conserve aussi un enregistrement de génération dans le dépôt.
  7. Une étape exécutée avec la condition always() supprime les fichiers temporaires du runner et demande la suppression du fichier source privé.

Le workflow de rendu possède une limite d’exécution de 90 minutes. Ce délai est une limite de sécurité du job, pas une promesse qu’un rendu sera terminé dans ce temps.

Le temps de traitement varie selon la résolution, le nombre d’images, la complexité JavaScript, les effets Canvas, les polices, les ressources distantes et la disponibilité du runner. Une fréquence élevée, une grande résolution ou une longue durée augmentent le volume de calcul et de données. Le mode générique peut prendre plus longtemps que la durée de la vidéo, car il capture en temps réel puis assemble les images.

Si le journal signale des captures trop lentes, réduire la fréquence ou l’échelle peut améliorer la réussite du rendu, au prix d’une fluidité ou d’une définition inférieure.

6. Erreurs, relance et reprise

  • Le démarrage de Chromium et le chargement de la page disposent de délais d’attente. Les erreurs de chargement des ressources, de connexion DevTools ou de fermeture/crash du navigateur sont identifiées comme potentiellement transitoires.
  • Le moteur peut relancer une fois le rendu après une erreur Chromium/réseau reconnue, avec une courte attente. Les erreurs permanentes, les fichiers invalides et les échecs d’encodage ne sont pas automatiquement réparés par cette relance.
  • Si FFmpeg échoue, le workflow échoue et les détails disponibles sont inscrits dans les journaux. Une vidéo incomplète n’est pas considérée comme publiée.
  • L’interface peut reprendre le suivi d’une tâche existante. Cela reprend le suivi des statuts et journaux, pas le calcul à partir de la dernière image : aucun mécanisme de checkpoint image par image n’est implémenté.
  • À la fin ou à l’échec du job, le nettoyage des fichiers temporaires est tenté. Si l’authentification OIDC ou l’appel de nettoyage échoue, le nettoyage planifié des sources anciennes constitue un filet de sécurité.

7. Import d’URL et ressources distantes

L’import direct depuis une URL est plus restrictif que le chargement des ressources d’une page pendant le rendu :

  • l’adresse d’import doit utiliser HTTPS sur le port standard 443, sans identifiant ni mot de passe intégré ;
  • la longueur de l’URL est limitée à 2 048 caractères ;
  • les adresses locales, privées ou non publiques sont refusées après résolution DNS ; les réponses DNS sont vérifiées et épinglées pour la connexion ;
  • trois redirections au maximum sont suivies ; le téléchargement est soumis à un délai maximal de 20 secondes et à une limite de 50 Mo ;
  • les URL GitHub de type fichier « blob » et les Gist sont normalisées vers leurs points de téléchargement brut ;
  • le chemin de la ressource importée doit désigner un fichier HTML/HTM compatible.

Ces règles protègent l’endpoint d’import contre les destinations locales et les téléchargements excessifs. Elles ne garantissent pas que toutes les ressources référencées à l’intérieur du HTML seront accessibles au moteur de rendu. Les ressources distantes peuvent être bloquées, lentes, supprimées, protégées par authentification ou soumises à CORS.

8. Sécurité des fichiers HTML et ZIP

  • Le stockage Backblaze B2 utilisé pour les sources et les vidéos est privé ; les transferts s’appuient sur des URL signées à durée limitée.
  • Les échanges du runner avec les API sont authentifiés par GitHub OIDC et liés à l’identifiant d’exécution attendu.
  • Les archives ZIP sont vérifiées : chemins absolus ou sortant du dossier, liens symboliques, fichiers spéciaux, doublons et archives dépassant les limites sont refusés.
  • Les contrôles d’origine, les validations d’identifiants et de tailles, ainsi que Cloudflare Turnstile protègent plusieurs opérations sensibles de l’API.
  • Le moteur exécute toutefois le JavaScript fourni dans Chromium. Les fichiers importés doivent donc être considérés comme du code actif, et non comme de simples documents. N’importe pas de fichier dont la provenance ou le contenu n’est pas fiable.

Limite de sécurité à connaître : le Chromium du moteur est lancé avec l’option --no-sandbox dans l’environnement de rendu. Les contrôles d’import et l’exécution dans un runner temporaire ne constituent pas une garantie d’isolation complète contre un HTML malveillant. La page d’aperçu utilise également une politique de contenu permissive pour permettre l’exécution des animations. Évite les contenus non fiables et les données sensibles ; une isolation renforcée du navigateur doit être considérée comme une amélioration de sécurité distincte.

9. Conservation et suppression

  • Sources HTML/ZIP : le workflow tente de les supprimer à la fin du job. Un nettoyage planifié sur Vercel cible les fichiers entrants âgés de plus de deux heures ; il s’exécute chaque jour à 03:17 UTC. Il s’agit d’un délai de nettoyage, pas d’une garantie de suppression à la seconde près.
  • Vidéos et miniatures : les métadonnées définissent une expiration à 30 jours après publication. Un workflow GitHub Actions de nettoyage s’exécute toutes les six heures et supprime les vidéos, miniatures et métadonnées expirées ; chaque exécution traite au plus 250 vidéos.
  • Suppression manuelle : l’action de suppression retire la vidéo, sa miniature, ses métadonnées, le fichier source associé et l’enregistrement de progression. Le code de stockage parcourt également les versions d’objets B2 pour supprimer les versions et marqueurs correspondants.
  • Liens signés : les URL de téléversement expirent après 10 minutes ; les URL de lecture/téléchargement signées expirent après 5 minutes.

La suppression dépend de la disponibilité des services tiers et de la réussite des tâches de maintenance. Les journaux GitHub Actions et les métadonnées techniques nécessaires au suivi peuvent exister séparément des fichiers vidéo.

  • Les vidéos expirent au bout de 30 jours au maximum et peuvent être supprimées plus tôt par leur propriétaire.
